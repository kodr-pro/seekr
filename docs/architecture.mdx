# Architecture

How seekr is laid out on disk and in code.

## Crates / modules

```
src/
├── wrangler/       AiWrangler MCP client (spawn, JSON-RPC, verdict parsing)
├── jockey/
│   ├── dag.rs      TaskDag + validation (schema, topo order)
│   ├── planner.rs  frontier Phase 0 (clarify-or-DAG)
│   ├── worker.rs   bounded-context SLM worker + tool definitions
│   ├── interceptor.rs  deterministic action review (paths, blocklist, loops)
│   ├── tools.rs    tool execution inside the sandbox
│   ├── driver.rs   the governor: phases, budgets, events, run state
│   ├── ledger.rs   cost tiers + append-only event log
│   └── cli.rs      roles, headless runners, doctor, ack/merge/clean
├── sandbox/
│   ├── git.rs      linked worktrees, checkpoints, rollback, patches
│   ├── paths.rs    fail-closed path containment
│   └── exec.rs     blocklisted command execution with timeouts
├── ui/             TUI (jockey dashboard + control center menu)
├── api/            OpenAI / Anthropic / Gemini provider clients
├── config.rs       config.toml (providers, agent, [jj])
└── bin/
    └── mock_aiwrangler.rs   scenario-driven MCP server stand-in
```

## On-disk layout

- **Worktrees** — each run gets `<repo>/../.jj-worktrees/<run-id>` on
  branch `jj/<run-id>`. Verified steps checkpoint there; failed attempts
  hard-reset. Merge with `seekr merge`; the branch always survives.
- **Run state** — `~/.local/state/seekr/jockey/<run-id>/`:
  `state.json` (DAG + ledger + status, written on every event),
  `events.jsonl` (the full log), and `wrangler/` (the generated gate
  config's ledger and semantic cache).
- **Config** — `~/.config/seekr/config.toml`.

## Process model

A `seekr run` is one process: the governor, the worker's HTTP client,
and one spawned `aiwrangler-mcp` stdio subprocess. Verification commands
run as short-lived children of the worktree. Nothing listens on a port;
the only network egress is your model endpoints and
`api.typesafe.ai` (AiWrangler's semantic battery).
